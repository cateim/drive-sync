## [Unreleased]

### ✨ Added

- Status headline for drive-sync: in sync, syncing now (phase, files listed and a progress bar against the usual run time), resync in progress, failed with its cause and how to recover, cut off, runs skipped, timer off, and no sync for a while.
- Warning chips for a timer that is off or will not start on boot, and for conflict copies waiting in `~/Drive`.
- Runs tab with the last 40 runs from the log, each with the changes on each side, file by file, and its errors (selectable to copy).
- Conflict copies tab listing every `*.conflictN` file in `~/Drive`, newest first; `Enter` shows the picked one in the file manager.
- Keyboard shortcuts (`Space`, `Tab`, `1`, `2`, arrows, `J`, `K`, `Enter`, `B`, `N`, `?`, `Q`) and a `?` overlay that lists them.
- A state glyph beside the headline: a cloud with a check when in sync, with arrows while syncing, with an alert on trouble.
- `drivesync status` prints the state without a window, as one line or, with `--json`, as a versioned JSON object for the bar and scripts.
- A widget for the Omarchy bar, shipped in the package, showing the same state as the window: last sync, last and next run, what failed, conflict copies, and buttons to sync now, open DriveSync and open `~/Drive`.
- The window links the widget into Omarchy's plugin folder and offers to put it on the bar (`B`); `N` says no, and the offer does not come back.
- Follows the Omarchy accent, window rounding and language live; ships English and Brazilian Portuguese.
- Package with `.desktop` entry and icon, installed by `bin/install`, so the app appears in the Omarchy launcher.
- Takeover of an existing drive-sync (`T` in the window, `drivesync takeover`): DriveSync's packaged user units run the same rclone command with the same remote, folder, listings and filters (moved with their `.md5`), so no resync is needed. The old units and scripts move to `~/.local/share/drivesync/taken-over/` with a manifest, nothing is deleted, a failed step undoes every step before it (when an old file cannot move back, every drive-sync timer is left off and the error says where it is), and `drivesync takeover --undo` goes back. The window names what blocks a takeover (a run going, a failed last run, units it cannot keep).
- Sync now, pause and resume from the window (`S`, `P`, `U`), the bar (`S`, `P`) and the command line (`drivesync sync`, `pause`, `resume`). A pause lasts one hour, until the next 8:00 or until resumed, survives a reboot and shows as "Paused" instead of a failure or "no sync for a while".
- Desktop notifications from DriveSync itself: a critical card with the cause when a run fails, a reminder every hour while it keeps failing, a note when runs work again, an hourly check for a timer that is off, not enabled or not loading, and a daily reminder of a pause with no end.
- `drivesync run` refuses to start rclone when the filters' `.md5` is missing or stale, because one bisync run in that state throws its base away until a resync.
- The status JSON is version 2: `managed`, `paused` and `pausedUntil` join the 17 keys of version 1.
- `T` during a run arms the takeover: the dialog opens by itself once the run ends, since runs take about half of each 15 minute tick. A takeover confirmed just as a run starts waits for that run and then happens, where it used to fail with "running".
- `?` in the bar panel lists its keys, in place of the key names beside the icons, which cut the last one off. The key that opens DriveSync from the panel is now `W`: `l` moved the cursor, so `L` only worked with Shift.
- `drivesync run` adds `--fast-list` to the bisync command unless the config turns ListR off. Against Google Drive the listing went from 476 s to 40 s for 33k files, with the same listing, so a run takes about a minute instead of eight; it needs no resync.
- `bin/harness` draws the window offscreen over a made-up drive-sync and saves it as a PNG, without opening anything on the desktop. The window pictures in the README come from it.
- The window opens `~/Drive` with `O` or its "Open the folder" button, as the bar does, through the running file manager.
- Fix a broken sync from DriveSync (`F` in the window, `drivesync fix`): after lost listings, listings out of sync or edited filters, it rebuilds the base of both sides with `~/Drive` still in use, as `drive-sync.sh resync` did, in its own unit (`drive-sync-fix.service`), so closing the window or logging out does not stop it halfway. A dry run lists the copies first, each with its direction and the ones to the notebook on top (where a file deleted there would come back), and nothing changes until it is confirmed; files that changed on the notebook during the base run are kept, and files that changed in the cloud, or appeared only there, are asked about one by one (`C` keeps the cloud's, `L` the notebook's, sending a cloud-only file to the Drive trash). Timer ticks, `S` and the bar's sync wait until the fix ends; a fix that waits for an answer or stops sends a card at once and every hour after. The fix is refused where the config's `runOnlyWhen` says no (the emergency home) and after `--max-delete` stopped a run, since a resync would bring the deleted files back; once the base ran, `X` asks twice before throwing it away.
- The fix's dry run and base run pass `--max-lock 2m`, so a base run killed halfway leaves a lock that expires 2 minutes later, and the retry waits it out (the final normal run keeps the config's own, 2m after a takeover). The old script's base run had no `--max-lock`, and a killed one blocked every later run for good.
- The status JSON and the bar know three new statuses, still in version 2: `fixing` (with `resync` true, so the bar shows the resync icon), `fixWaiting` and `fixFailed`.
- After `--max-delete` stopped a run, DriveSync shows what that run would delete instead of a fix (`D` in the window with the first 500, `drivesync deletes --list` with all of them): split by side, the ones gone from the cloud (deleted on the notebook, for good) first, the others going to the Drive trash. Typing the number of files in the list lets one run through (`drivesync deletes --allow <count>`) with the guard raised just enough for them, never `--force`; that run first checks with a dry run that it would delete only files in the confirmed list, and otherwise keeps the usual guard and stops again with the new list. The confirmation serves one run, only while the stopped run is still the last one, and expires after 30 minutes. The headline counts the files, and the card (still critical) and the bar say to press `D`. A stop of tens of thousands of deletions is read whole, past the 3 MB of log the status reads. Filters edited after a stop no longer bring `F` back: the window and the card say to undo the edit first, so the next run shows the list.
- A project page at <https://cateim.github.io/drivesync/>, in English and Brazilian Portuguese, with the privacy policy and the terms of service that Google's sign-in screen links to: DriveSync runs on your computer, your files travel only between it and Google, and the developer runs no server and receives no data.
- First setup where no drive-sync exists (`T` in the window, `drive-sync signin` then `drive-sync setup --folder <path>`): Google sign-in in the browser through rclone's own flow and the DriveSync client, so the token goes from Google into `rclone.conf` and never through DriveSync; the folder (`~/Drive` by default, files already in it are kept); generic default filters (`.git`, `node_modules`, `.venv`, Python caches, Google Docs shortcuts, system junk); a config with the flags the maintainer's sync proved; then the fix's dry run in both directions, which nothing passes before you confirm. The fix's mark is written before the timers come on, so no tick runs before the base. A sign-in cancelled, left in the browser or stopped with Ctrl+C removes the half-made `drive-sync` remote, and only rclone is stopped, never the browser; when the browser does not open, the dialog shows rclone's local sign-in address. A `drive-sync` remote DriveSync made earlier is reused (signed in again when its token is dead), one made by hand is never touched. Setup refuses an existing drive-sync (take it over instead), the home folder itself, a folder that holds or sits inside `~/.config`, `~/.local/state` or DriveSync's and rclone's own folders, an existing filters file and rclone older than 1.66. Cancelling the first fix before its base undoes the setup and offers it again; a run refused because no first sync was ever confirmed says so and offers `F`.
- Sign in again (`I` in the window, `drive-sync signin`): a run that Google refuses for an expired or revoked token has the cause `signIn`, and the window, the critical card and the bar say to sign in again instead of repeating rclone's `rclone config reconnect`, which needs a terminal. The browser sign-in refreshes the config's own remote with its own client (and its `--config`), then a run starts. A fix that stopped on the token asks the same, then `F`. Only Google's refusals count (`invalid_grant`, `invalid_client`, `unauthorized_client`, an expired token): a network failure while fetching the token stays an ordinary error.
- The Google client is compiled in only from the git-ignored `src/oauthclient.local.h` (template `src/oauthclient.local.h.example`); a build without it says it has no Google client.
- Settings (`,` in the window, `drive-sync settings`): the sync interval (5 min to 4 h in the window, kept in the config and written into a drop-in for the packaged timer, none at the usual 15) and the max-delete guard (1% to 50%, only lower after a stop, whose deletions go through `D`) apply at once. The local folder, the filters (an editor that checks the rules with rclone first) and the cloud folders that come down go through the fix, whose dry run you confirm; cancelling that fix before its base run puts the old config and filters back byte for byte, so the sync goes on with its old base. The fix writes the new config and filters itself, once no run is under way, so a run already started never meets new filters with the old base's `.md5`. The old folder is left as it is, outside the sync, and undoing a takeover is refused after a folder change until the folder is set back. Folder names that look like options (`--json`) work in `drive-sync settings`, `setup` and `folders`, and the window sends the edited filters on stdin.
- Selective sync: a tree of the cloud's folders, read a level at a time with `rclone lsjson --dirs-only` (`drive-sync folders`), with nothing copied. Unticked folders become rules in a marked block at the top of the filters file and stay whole in the cloud; one that was synced keeps its copy on this computer, outside the sync, and the window names it. Ticking a folder again warns that its local copy goes back to the cloud, files deleted there meanwhile included. First setup offers the same tree before its dry run (`drive-sync setup --skip`).

### 🔧 Changed

- The takeover looks for the bisync listings of its own two paths, by the name rclone gives them, so a stale session left in the work dir no longer passes for them.
- Edited filters are a cause, not an alarm: the window, the bar and a normal card say to press `F`, where a critical "Drive stopped syncing" card used to repeat every hour. Lost listings and listings out of sync say "Press F" too once DriveSync runs drive-sync, instead of `drivesync takeover --undo` and `drive-sync.sh resync`.
- The app is now DriveSync, and its machine name is `drive-sync` (it was SyncWatch, then `drivesync`, which the AUR already uses for an unrelated Google Drive client, so `yay` kept offering that package as an upgrade of this one): the command, the package and the bar widget id are `drive-sync`, the package replaces `syncwatch` and `drivesync`, and the window's class and launcher entry follow. The first `drive-sync` command moves `~/.config/{syncwatch,drivesync}` and `~/.local/share/{syncwatch,drivesync}` to `~/.config/drive-sync` and `~/.local/share/drive-sync`, and `~/.local/state/{syncwatch,drivesync}` to `~/.local/state/drive-sync-app` (`~/.local/state/drive-sync` is the old `drive-sync.sh`'s), keeping the filters and their `.md5` byte for byte, so no resync is needed, and points the config and the takeover backups at the new folders. The widget takes the old one's place on the bar by itself the first time the window opens. The takeover lock is held by a process named `drive-sync`, `drivesync` or `syncwatch` by its exact name, no longer by a piece of its command line.
- The icon is now the cloud and check badge on their own, with a dark outline instead of the dark tile, so it reads on light and dark backgrounds. The Google sign-in screen logo (120 px PNG) is rendered from the same file.
- The run let through after a `--max-delete` stop moves the notebook files it deletes (and the ones it overwrites) to `~/.local/state/drive-sync-app/allowed-backup/<time of the stop>` with `--backup-dir2`, instead of deleting them for good. Afterwards DriveSync compares what it deleted with the list you confirmed: anything more is written to the log, shown in the window and on a critical card, with where it went.
- The raised guard for that run is counted per side against each side's own listing, as bisync checks it, so a stop where the smaller side holds more deletions no longer falls short and stops again.
- "Late" (no sync for a while) is three sync intervals with no successful run instead of a fixed 45 minutes, in the window, the status JSON's `status` and so the bar; 45 minutes at the usual 15-minute interval.

### 🐛 Fixed

- The shortcuts card no longer runs off the top and bottom of a short window: it scrolls (also with the arrows and `J` `K`) when it is taller than the window.
- Clock times show 12 or 24 hours like the clock on the Omarchy bar, in the window, the bar panel and the notifications, and follow a right click on that clock. The window showed AM/PM whenever Omarchy was in English, even with the bar clock on 24 hours, and the panel always showed 24 hours.
- `drivesync --help` (and `-h`, `help`) prints the usage. It opened the window, like every argument that starts with a dash.
- A warning on the bar (conflict copies, a late, skipped or interrupted run) turns the cloud and the panel icon orange, the same orange as the window. It looked just like an up-to-date sync.
- A log with no run in it (new, or just rotated) shows "No sync in the log yet" as a warning in the window and on the bar. It showed a green "In sync", and the bar "Synced at -".
- A failure only systemd saw (the log ends in a good run) says it is failing since the service's last start, not since that good run.
- The failing line in the bar panel has a sentence for a run stopped at its time limit and for a failure only systemd reports, and is never blank.
- When `omarchy plugin list` fails as the window opens, the window no longer says it could not put DriveSync on the bar: nobody asked yet. After `B` it still does.
- `N` also hides the notice that someone else's folder or link holds the widget's place, which came back at every start.
- A run let through that stops again at the guard gets its card at once, and the window says why it kept the usual guard. So does a stop with a different list; the same stop at every tick still waits for the hourly card.
- A dry run of the run let through that never reached bisync no longer counts as finding nothing: the usual guard stays.
- `D` and `drive-sync deletes --allow` agree on a fix whose last step failed after a guard stop, even when that step failed on an answer and not on the guard. `D` is off while a run is under way, and its dialog closes when a run starts or the stop is gone.
- Reading a guard stop longer than the log's 3 MB tail reads each earlier chunk once, and a file named like a run's start line no longer cuts the search short.
